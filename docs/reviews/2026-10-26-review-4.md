## F06 Payments and publishing

### Critical

- [Critical] payments · `app/modules/payments/services/orders-paid.js:140-152` (both reviews; with `core/events.js:150-171`, `platform/services/webhooks.js:108`): `orders/paid` does all its work before it answers: fulfilment (2+ Admin calls), then `await publish(PaymentReceived)`, which waits for every `ListingWentLive` listener (media photo copy with S3 + sharp per photo, publishing sync with 3–6 Admin calls, the live email through SES), then the period and duplicate checks. 9–10 s measured against Shopify's 5 s timeout, so deliveries time out and are retried, and repeated failures put the subscription at risk → in the request keep only `readOrder`, `mismatch()` and the `FeeCharge` insert (new `appliedAt`, null); apply the payment (publish, fulfil, period, set `appliedAt`) in a job started after the reply, with a scheduler backstop, idempotent on `orderGid`. **→ F06-FIX-2**
- [Critical] payments · `app/modules/payments/services/tasks.js:93-99`: nothing reconciles paid fee orders. `runLapse` lapses every awaiting-payment listing past `paymentDueBy` without asking Shopify, so a listing whose `orders/paid` was lost (as in QA) is lapsed although the seller paid; a late delivery then hits NOT_PAYABLE, sets `refundFlag` and raises an incident → an hourly `payments.reconcile-paid-orders` (Admin `orders` query on paid orders with the `CLASSIFIEDS-FEE` SKU, recent window) feeding the same match + charge + apply path, also run inside `runLapse` before anything is lapsed. **→ F06-FIX-3**

### High

- [High] payments · `app/modules/payments/services/pay-page.js:53-69`: when a paid order's webhook was lost, the pay page still offers "Pay and publish", so the seller can pay twice (caught only later as `duplicate-fee-order`) → before `createCheckout`, look for a paid fee order carrying this listing's attribute (the reconcile query); if one exists, apply it and show "already paid". **→ F06-FIX-3**
