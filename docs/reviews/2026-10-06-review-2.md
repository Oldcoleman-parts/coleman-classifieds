## F03 — Email and photo services

### Medium

- [ ] **[Medium] media · `app/modules/media/services/uploads.js:160,179-185`** — AC1 of F03-FIX-1 ("both return the same photo") still fails in a second order of events. Request B passes `findOwn` before A commits. A then commits and deletes `incoming`, so B's `readObject` returns null and B throws `NotFoundError` instead of returning A's photo. The early full-listing branch (`:173`) can delete `incoming` in the same way while a request for the same photo is still running. → When `bytes` is null, or before rethrowing a read error, call `findOwn(photo, id)` again and return the row if one exists.
- [ ] **[Medium] media · `app/modules/media/tests/upload-race.test.js`** — two paths have no test: (a) the order of events above, where A finishes completely before B's `GetObjectCommand`; (b) an unexpected database error, where both files must be kept (`uploads.js:240-243,248-252`; the ticket notes admit this gap). → Add both tests. For (b), make `tx.photo.create` throw an error that isn't a validation error, then check that the `private/` and `incoming/` files are kept and that a retry succeeds.

### Low

- [ ] **[Low] media · `uploads.js:231-251`** (both reviews) — the ownership check and the delete aren't atomic. The lock is released before `cleanup([storedKey, incoming])` runs. Suppose a concurrent `deletePhoto` makes room and a request for the same photo then inserts its row. The refused request can still delete the `private/` file that row points to, which is the original symptom, though the window is very narrow. → On a refusal, keep `storedKey` and delete only `incoming`, or give each attempt its own private key that is stored on the row.
- [ ] **[Low] media · `uploads.js:197,248-252`, `services/retention.js:37`** (security) — `private/` files can be left with no `Photo` row: files are kept on purpose after a database error, and `deletePhoto` can race a repeat completion. Retention only removes keys that have a row, so these files (already stripped of metadata) outlive the retention period. → Add a daily sweep of `private/<listingId>/*` objects older than 1 day with no live row, or use an S3 lifecycle rule plus tags. This overlaps with the review 1 Medium about takedown.
- [ ] **[Low] media · `uploads.js:240-243`** (code) — the bare `catch { throw error; }` swallows the error from the lock check without logging it. → Log its `name` with `console.error`, as `cleanup` does.
- [ ] **[Low] media · `services/store.js:53-67`** (code) — `deleteObjects` now throws on per-key `Errors`, which changes how `retention.js:37`, `publish.js:119,141` and `photos.js:136` behave. Retention stops at the first listing with a failed delete. → Make sure the review 1 "takedown isn't reliable" item explicitly covers retention.
- [ ] **[Low] media · `uploads.js:64-66,115-122`** (code) — the JSDoc for `findOwn` and `countPhotos` leaves out the optional `db`/`tx` parameter. → Add `@param {import("@prisma/client").Prisma.TransactionClient} [db]`.
- [ ] **[Low] media · `tests/upload-race.test.js:385-395`** (code) — the `console.error` spy isn't restored if `completeUpload` throws, and the test labelled "SEC:" doesn't say what it checks. → Restore it in `afterEach` with `vi.restoreAllMocks()`, and rename the test.
- [ ] **[Low] docs · `docs/features/03-email-and-photos/README.md`, `tickets/F03-T2.md`** (code) — F03-T2 went from In progress back to To do in this range, with no reason recorded. → Confirm that reopening it was intended and link it to review 1, or restore the status.
