Most steps are done by a human; follow `docs/reference/railway-setup.md`. The repo side already exists from F01-T1: `Dockerfile`, `railway.json`, `shopify.app.staging.toml` (placeholders), `.github/workflows/ci.yml`.

## Scope

- [ ] **GitHub:** add the remote and push (a human does this); the CI workflow runs lint and `test:ai`.
- [ ] **Railway:** an OCP-owned project with the app service, PostgreSQL (daily backups on) and the hourly cron calling `/jobs/run`.
- [ ] **Env vars:** set everything from `docs/architecture/shopify-config.md` on the app service, including the AWS, SES, CloudFront, Turnstile and ops values added by F03, F07 and F08.
- [ ] **Staging app:** create “Coleman Classifieds (staging)”, fill in `client_id` and the Railway domain in `shopify.app.staging.toml` (four `REPLACE_WITH_RAILWAY_DOMAIN` places), bring its scopes, webhooks and app proxy in line with `shopify.app.toml`, then `shopify app deploy --config staging`.
- [ ] **Distribution:** decide whether `app/shopify.server.js` keeps `AppDistribution.AppStore` or moves to single-merchant distribution for this custom app.

## Out of scope

- Backups to S3, incident alerts and the launch checklist (F08-T2).
- The production deploy (F08-T2, done by a human).

## Acceptance criteria

- [ ] CI passes lint and tests on GitHub.
- [ ] The Railway deploy log shows every migration applied by the `setup` script (`prisma generate && prisma migrate deploy`).
- [ ] The staging app opens embedded in the dev store admin, and a `Session` row exists in the Railway database.
- [ ] The hourly cron gets a 200 JSON summary from `/jobs/run`; a call without the secret gets 401.

## Notes

- The database user in `DATABASE_URL` must be allowed to create roles: the initial migration creates `classifieds_purge`.
- `shopify.app.staging.toml` was copied from the template config in F01-T1, so it lacks whatever F01-T2 and later tickets add to `shopify.app.toml`.
