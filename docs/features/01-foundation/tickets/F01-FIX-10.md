## Scope

- [x] `countAuditEntries({ action, listingIds, since })` → `Map<listingId, count>` (listings with none left out), one `groupBy` on the `[action, at]` index.
- [x] `listingsWithAuditEntry({ action, listingIds, since })` → `Set<listingId>`.
- [x] Both exported from `core/index.js` with JSDoc, inputs validated (`action` a non-empty string, `listingIds` through `requireIdList` with at most 500, `since` a `Date`). They return ids and counts only, never `details` or the actor.
- [x] Update `app/modules/core/CLAUDE.md`.

## Out of scope

- Switching ops to them ([F08-FIX-6](../../08-operations-and-launch/tickets/F08-FIX-6.md)).
- The direct audit reads in access (`services/invitation-email.js:227`) and console (`services/history.js`, `services/health.js:26`): list them in Notes as follow-ups for F04 and F05; history export and Health need more than counts.

## Acceptance criteria

- [x] Counts include only rows of that action, those listings and `at >= since` (test).
- [x] An invalid `action`, more than 500 ids or a missing `since` is a `ValidationError` (test).
- [x] `npm run test:ai -- app/modules/core` is green.

## Notes

- Built in a new `core/audit.js` (read-only; audit writes stay in `events.js`): `countAuditEntries()` makes one `groupBy` on `action`, `listingId IN` and `at >= since`, and `listingsWithAuditEntry()` returns the keys of that count. Exported from `core/index.js`. An empty id list makes no query, though the input is still validated. An entry exactly at `since` counts (`gte`, as ops does today).
- Validation: `action` uses `requireString` (at most 100 characters, trimmed), `listingIds` uses `requireIdList` (at most 500, duplicates dropped), and `since` must be a valid `Date`. All throw `ValidationError`.
- `// DECISION:` Postgres may use the `[listingId, at]` index rather than `[action, at]`. Both fit, so the schema is unchanged. There is no `tx` option, because no caller needs one yet.
- Follow-up for F08-FIX-6: the helpers take ids, so ops first selects its candidate ids (closed, page set, past the cutoff), calls in chunks of 500, and applies `>= maxFailures` itself.
- Follow-ups for F04 (access) direct audit reads: `services/invitation-email.js:201` (`countResends`, inside `tx`, which would need a `tx` option) and `:227` (the latest `InvitationResent` details), plus `services/invitations.js:85` (through `tx`).
- Follow-ups for F05 (console): `services/history.js:134,202,228` (history and export need full rows) and `services/health.js:26` (a global `EmailProblem` count with no listing ids, which needs a `countAuditAction({ action, since })` helper or a notifications provider).
- Tests: `core/tests/audit-counts.test.js` (filtering by action, ids and `since`; the Set; the `ValidationError` table; an empty id list; no details or actor in the result). The empty-list test checks the result only, not that no query ran. `npm run test:ai -- app/modules/core` → `✓ 248 passed · 0 failed`.
