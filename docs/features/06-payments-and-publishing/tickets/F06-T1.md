## Notes

_Record decisions (`// DECISION:`), deviations and follow-ups here. Code review and security audits are run on demand (`/review-all`), not per ticket._

- From F03-T1: emails are sent with `notifications.send(key, to, vars, { replyTo, idempotencyKey })` (keys, placeholders and `sensitive` flags in `app/modules/notifications/registry.js`). Approval sends `approved_pay` (`fee_amount`, `payment_due_date`, `pay_link`) and the reminder sends `payment_reminder`.
- From F03-T1: links passed as placeholders (`pay_link`) must be https. A `sensitive` template (private link) is never queued: `send()` returns `{ status: "FAILED" }` if SES is down, and the caller must cope (show an error or retry later).
- From review 1: do F01-FIX-1 and F01-FIX-2 before this ticket. They change how a failed `PaymentReceived` → `PAY` is reported and how a webhook that died mid-handler is retried, and every webhook handler must be safe to run twice.
- From F01-FIX-2: a webhook handler may run twice for one delivery. A delivery whose handler did not finish within 60 s (crash, redeploy, timeout) is taken over by the next retry, and a handler that throws is run again at once. The `orders/paid` and `refunds/create` handlers must be idempotent from the first line (`FeeCharge` by unique `orderGid`, tag and fulfilment only if missing). They must also finish well inside 60 s, ideally under Shopify's 5 s timeout: while a delivery is in flight a retry answers 500, and a handler slower than 60 s would run twice at the same time.
- From F01-FIX-1, how `orders/paid` must publish `PaymentReceived`:
  - `await publish(EVENTS.PaymentReceived, …)` inside the webhook handler and never catch it. A rejection means "temporary failure": the webhook must answer 500 so Shopify retries.
  - Save `FeeCharge` idempotently (`orderGid` is unique) before publishing, and publish again on a retried delivery even when the charge row already exists.
  - Check that the listing exists before publishing: the event's audit entry has a foreign key to the listing, so an unknown id rejects on every retry.
  - A publish that resolves does not mean the listing is live. Read `getListingSummary()` afterwards: when it is not live, core has set `refundFlag` and written a `PaymentNotApplied` audit entry, and payments raises the late-payment incident.
  - Core treats any `PaymentReceived` for a listing that is already live as a repeat. Spotting a second, different order for the same listing is the job of payments.
- **Decision (2026-10-08, user):** fee orders are not tagged. The fee variant carries the SKU `CLASSIFIEDS-FEE`, and ShippingEasy excludes fee orders by that SKU. So the `write_orders` scope is not added and no re-auth is needed. This replaces "tag" in the `orders/paid` scope line.
- **Finding (2026-10-08):** the fee product uses the product status **Unlisted** (Admin API 2025-10 and later). Shopify hides an unlisted product from store search, collections, recommendations, the sitemap, internet search and Shopify Catalog, while cart, checkout and orders treat it as active. The Storefront API returns it only when it is asked for by id or handle. Still to check on the dev store in the fee-setup step: that the app's storefront token can put the variant in a cart (which sales channel the product must be on).
- The app adopts an existing product with the handle `coleman-classifieds-listing-fee` before creating one, so staff may create the fee product by hand.
- **Built (2026-10-08).** No schema change and no `shopify.app.toml` change. New env requirement: `SHOP_DOMAIN` must be set wherever the app runs (payments reaches Shopify outside a request). Optional `FEE_TEST_ORDERS=allow` for a staging app on a dev store.
- **Decisions** (each has a `// DECISION (F06-T1)` in the code):
  - **D1 setup:** `ensureFeeSetup()` runs when first needed (first approval or checkout), under a database advisory lock; the product is found by handle before it is created.
  - **D2 selling plan group:** not created here. It needs `write_purchase_options`, which `shopify-config.md` assigns to F09. Deviation from the first scope line, agreed with the user.
  - **D3 pay link:** a signed reference `<listingId>.<signature>` bound to `paymentDueBy`, served by payments at `/apps/classifieds/pay/:ref`. Only the hash of a seller link is stored, so `<seller link>/pay` cannot be put in an email. The seller page keeps its "we've emailed you a payment link" text.
  - **D4 discount code:** derived by HMAC from the listing id and `paymentDueBy`; only its Shopify id is stored. It is valid one day past the deadline so a checkout opened in time can finish.
  - **D5 emails:** `approved_pay` and `payment_reminder` are retried up to three times, an hour apart, through the try number in the idempotency key.
  - **D6 mismatch:** paying the full price (discount removed), a wrong variant, quantity or code, or shipping lines → no `FeeCharge`, no publish, a payment problem. In production a test order is a mismatch too.
  - **D7 late payment:** "late" means the listing has lapsed. A payment that lands after `paymentDueBy` but before the lapse task runs still goes live.
  - **D8 refund:** the charge becomes `REFUNDED` and a problem is raised; the listing and `Listing.refundFlag` are not touched.
  - **D9 incidents:** `reportPaymentProblem()` writes a `PaymentProblem` audit entry and a log line until F08-T2 provides `ops.raiseIncident()`.
  - **D10 fee is not taxed** (`taxable: false`); OCP's accountant should confirm.
  - **D11 reads:** `services/facts.js` reads `Listing` and `Invitation` directly (read-only).
