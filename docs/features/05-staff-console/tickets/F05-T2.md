### 2026-10-07 build

Decisions (approved with the plan):

- **D1** Console reads `AuditEvent` directly, read-only (`services/history.js`). Core has no audit reader, and the feature README already says console "reads most tables".
- **D2** Console never reads or writes `BuyerMessage` or `OpsIncident`. The owning modules plug in through `setMessageProvider()` and `setHealthProviders()` (`services/providers.js`); without a provider the screen shows "not available yet".
- **D3** Console writes the staff audit entry for release, discard and resolve (`HeldMessageReleased`, `HeldMessageDiscarded`, `IncidentResolved`) once the provider reports `changed: true`. It is not in the same transaction as the owning module's change. A repeat writes nothing.
- **D4** Export columns: `at, listingId, action, actor, actorRef, transition, from, to, details`. No seller name, email or phone, and no join to `Invitation`. `details` is exported as stored, except a `to` key outside a status change (the recipient of a test email) is dropped. `actorRef` carries the staff email.
- **D5** The CSV comes from a separate POST-only resource route, `/app/history/export-csv`, because an export is audited (`HistoryExported`) and must not run on a prefetch. The page is `/app/history/export`.
- **D6** A date-range export needs both dates, at most 366 days, read in the shop timezone, with the end date inclusive.
- **D7** An export ends at the newest event at the moment it starts, so its own `HistoryExported` entry is not in its file.
- **D8** The review screen shows the newest 200 history entries; the export has them all.
- **D9** Resolving an incident has no confirmation modal (not destructive). Discard has one.
- **D10** The CSV also neutralises cells starting with a tab or carriage return, beyond the `= + - @` in the security skill.

Follow-ups (other features; console needs one line of wiring for each):

- **FU1 (F07-T1)** `contact` exports `listHeld()`, `release(id, staff)`, `discard(id, staff)`, each returning `{ changed, listingId }`, and registers them with `setMessageProvider()`. Release must be atomic (`HELD → RELEASED`) and send exactly once; the real "double release sends once" test belongs there.
- **FU2 (F08-T2)** `ops` exports `listOpenIncidents()` and `resolveIncident(id, staff)` and registers them as the `incidents` health provider.
- **FU3 (F08-T1)** `scheduler` keeps the last run and exports `getLastRun()` (`jobs` provider). Today the run summary is only logged.
- **FU4 (F08-T2)** `notifications` exports an SES health check (`email` provider). Until then Health shows only the count of `EmailProblem` entries.
- **FU5 (F06-T2)** `publishing` exports the storefront live count (`liveCount` provider).
