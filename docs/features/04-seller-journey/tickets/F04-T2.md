## Notes

_Record decisions (`// DECISION:`), deviations and follow-ups here. Code review and security audits are run on demand (`/review-all`), not per ticket._

- From F02-T2: `Settings.rulesText` is stored as plain text (no `<` or `>`, up to 20,000 characters, LF line breaks). Escape it as HTML when showing it to sellers (and escape Liquid delimiters if the proxy page returns Liquid), keep the line breaks, and store in `TermsAcceptance.rulesVersion` the version the seller was actually shown (`Settings.rulesVersion`, e.g. `v1`).
- From F03-T2: photo storage is ready in `app/modules/media`. Build the two proxy routes (`/apps/classifieds/upload-url`, `/apps/classifieds/upload-complete`) here: check the seller’s link and listing first, rate-limit the POSTs, then call `media.createUploadUrl({ listingId, actor, contentType, byteSize })` and `media.completeUpload({ listingId, photoId, actor })`. Media does **not** check the token; it trusts the `listingId` it is given.
- From F03-T2: in the browser use `uploadPhoto()` and `resizeImage()` from `app/modules/media/client.js` (resize, upload progress). Show photos with `media.listPhotos(listingId)`; its `previewUrl` links are private and last 10 minutes, so never put them on a public page. Reorder, main photo and delete are `media.reorder()`, `media.setMain()` and `media.deletePhoto()`; `deletePhoto()` also takes a live photo off the public site at once.
- From F03-FIX-2: media publishes **only approved photos** (`Photo.approvedAt`). New photos start unapproved. Put the photos a revision adds in `ListingRevision.photoIds`; staff approval passes them on `RevisionApproved`, and only then are they published. A rejected revision’s photos are never published, but delete them with `media.deletePhoto()` anyway to free the slots. A revision that replaces a photo must delete the old one once the new one is approved. Photos added while SUBMITTED or APPROVED_AWAITING_PAYMENT would stay unapproved: block uploads in those states or route them through a revision. `publish(listingId, { photoIds })` no longer exists.
- From review 1: do F03-FIX-2 (only approved photos may be published) before this ticket; it defines how a revision’s photos are marked approved. F03-FIX-1 (repeated upload completion) should also be done first.

### Built (F04-T2, 2026-10-06)

- No schema change. `workspace` module (new) renders the page and runs the actions; `access` is the gate (`gateSeller()`), with a new CSRF form token and the deadline check in `resolveToken()`. Routes: see the feature README.
- DECISION: INVITED shows an intro page with **Start my listing**; the draft (and its 14-day clock) starts on that POST, not on GET, so link scanners can’t start it. (data-model.md says “seller opens link”.)
- DECISION: a passed draft or correction deadline makes `resolveToken()` return CLOSED (reason DEADLINE) on every request; the EXPIRE transition and email stay with F08-T1.
- DECISION: CSRF token = HMAC (key from TOKEN_PEPPER, “cc-form-v1”), bound to the invitation, 24 h, sent as `csrf` or `X-CC-Form`; missing or bad → 403.
- DECISION: one inline script (inside `{% raw %}`) with `media/client.js` inlined; background calls send `X-CC-Device` and `X-CC-Form`. Upload routes are under the token path (`/apps/classifieds/seller/:token/upload-url`), not `/apps/classifieds/upload-url`, because the token identifies the listing.
- DECISION: photos may be added in DRAFT, CHANGES_REQUESTED and LIVE (no pending revision); not in SUBMITTED, APPROVED_AWAITING_PAYMENT, PAUSED. Reorder only before submission. On LIVE, the last approved photo and photos in a pending revision can’t be removed.
- DECISION: live photos stay unapproved until the seller presses “Send changes for review”; the server puts the unapproved photos in `ListingRevision.photoIds`. One PENDING revision at a time (advisory lock).
- DECISION: the agreement box is ticked on every submit (new and corrected); a stale `rulesVersion` is refused. `TermsAcceptance` (version, time, IP, user agent ≤512) is written before `SUBMIT` and deleted again if the transition fails.
- DECISION: field limits — title 5–120, description 20–5000, condition 120, known issues / contents 2000, availability note 120, city 80, state 40, arrangements note 200 (required with OTHER), price $1–$100,000, quantity 1–999. Plain text only (`<`/`>` refused). The seller name is a choice; the server stores the first name or “Private seller”.
- DECISION: no audit row for draft saves (content edits, not state changes); every state change and event is audited through `transition()`/`publish()`.
- Pay stage: placeholder text with `paymentDueBy` (F06). LAPSED shows a “payment window passed” page.
