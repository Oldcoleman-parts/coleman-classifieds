Start with `/implement-ticket F04-T3`. Needs F03-T4 (the `seller_link_request` email).

Added 2026-10-06 while planning F05-T1. Sellers have no account; each listing has its own invitation and private link, and only the link's hash is stored. This page lets a seller who lost their links get working ones by email.

## Scope

- [x] Proxy page `/apps/classifieds/my-link` (GET form, POST): email field, Turnstile and a honeypot; `noindex`, `Referrer-Policy: no-referrer`, theme layout.
- [x] POST finds every **open** listing whose invitation went to that address (case-insensitive, trimmed): INVITED, DRAFT, CHANGES_REQUESTED, SUBMITTED, APPROVED_AWAITING_PAYMENT, LIVE, PAUSED. Newest first, at most 20.
- [x] For each of them a new 32-byte link replaces the old one (only the new hash is stored, so the old link stops working at once), in one transaction, with an `AuditEvent` per invitation (actor SYSTEM, `SellerLinkReissued`, no token in it).
- [x] One `seller_link_request` email with all of them (F03-T4), sent to the invitation's stored address, not the typed one.
- [x] Always the same reply and the same response shape, whether or not the address is known; nothing is sent when it isn't.
- [x] Rate limits: per IP, and per email address (at most 3 a day; further requests change nothing and send nothing).
- [x] Export `getLinkUrl(admin, shop)` from `access/index.js` (the storefront URL of this page) for emails that show the help line.

## Out of scope

- A combined "My listings" page (possible later feature, needs a new kind of token).
- Email codes: confirming one listing on a device still doesn't confirm the others.
- Closed listings (SOLD, EXPIRED, REMOVED, REJECTED, LAPSED) are never included.

## Acceptance criteria

- [x] A seller with three open listings and one closed one gets one email with three working links; their old links show the invalid-link page.
- [x] An unknown address gets the same reply, no email and no change.
- [x] The fourth request in a day for the same address changes nothing and sends nothing; the IP limit gives 429.
- [x] Turnstile failure or a filled honeypot changes nothing.
- [x] Log spy: no token or link in logs or audit rows.
- [x] `npm run test:ai` is green for this feature.

## Notes

_Record decisions (`// DECISION:`), deviations and follow-ups here. Code review and security audits are run on demand (`/review-all`), not per ticket._

- Device credentials, email codes and form tokens are bound to the invitation, not the token, so replacing a link doesn't sign the seller out of a confirmed device.
- Someone who knows a seller's email can trigger new links, but the links only go to the seller's inbox; the daily limit keeps this from becoming a nuisance.
- Built: `services/my-link.js` (handlers and `reissueSellerLinks()`), `services/turnstile.js`, route `app/routes/proxy.my-link.jsx`; `getLinkUrl()` in `services/links.js`; `linkState()` split out of `resolveToken()` so "open" is exactly what the seller page accepts.
- DECISION: the audit action is `SellerLinkReissued` (PascalCase like every other action), details `{ invitationId }` only.
- DECISION: the email is sent first; the new hashes are stored only when SES accepted it. A failed or suppressed send changes nothing, so the old links keep working.
- DECISION: the per-address limit (3 a day) is in memory like the other limits (resets on deploy), keyed by the hashed address and counted for known and unknown addresses alike. Per IP: 10 POSTs an hour (429), 60 page views a minute.
- DECISION: lookup is `sellerEmail = <trimmed, lowercased>`; stored addresses are already lowercased by `requireEmail`. At most 20 links are reissued, so `more_count` stays empty.
- DECISION: Turnstile fails closed (no secret, no answer, error or timeout). A failed check re-shows the form (400); a filled honeypot gets the normal reply.
- Accepted: a known address answers a little slower than an unknown one; links only ever go to the stored inbox.
- Setup: `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` must be set (Cloudflare test keys for `shopify app dev`). Added by a human; this is the first ticket using Turnstile.
- Follow-ups: shared `platform.verifyTurnstile()` / `platform.rateLimit()` (F07 needs both); `docs/reference/railway-setup.md` should list F04-T3 as using Turnstile; F05-T1 / F08 pass `get_link_url` from `access.getLinkUrl()`.
- Tests: `app/modules/access/tests/my-link.test.js` (AC1 pulls the links out of the sent email: new ones resolve OK, old ones show "This link doesn't work"; AC2 compares the unknown-address reply with a known one), `my-link-security.test.js` (log spy, audit details), helpers in `my-link-helpers.js`. `my-link.test.js` is over the ~150-line guideline; split it when next touched.
- Manual QA (to run on the dev store, needs the Turnstile test keys): form at 360 px with the widget; two invitations for one address → one email with 2 rows, old links invalid; unknown address → same reply, no email; 4th request in a day sends nothing.
