## Scope

- [ ] `createInvitation()` (a transaction with the Listing; fee prefilled from promo/base and editable; offer scope) and the **Create invitation** screen: seller details, item summary, fee, offer scope, staff photos (F03 helper), the seller’s previous listings, and a copyable link + invitation email.
- [ ] `resolveToken()` (constant time; invalid, closed or expired states) and revoke; the 30-day expiry task registered with the scheduler.
- [ ] Email code check (when `emailCodeRequired`): 6 digits, 15 min, max 5 attempts, a signed device cookie for 30 days.

## Out of scope

- Anything listed in other tickets or features.

## Acceptance criteria

- [ ] A modified token shows the invalid page; a second listing per invitation is impossible.
- [ ] A later Settings fee change doesn’t change a locked invitation.
- [ ] A forwarded link on a new device can’t proceed without the code; brute force is locked after 5 attempts.
- [ ] Tokens and codes never appear in logs.
- [ ] `npm run test:ai` is green for this feature.

## Notes

_Record decisions (`// DECISION:`), deviations and follow-ups here. Code review and security audits are run on demand (`/review-all`), not per ticket._

- From F03-T1: every email is sent with `notifications.send(key, to, vars, { replyTo, idempotencyKey })`; template keys, placeholders and which are `sensitive` are in `app/modules/notifications/registry.js`. Links passed as placeholders must be https.
- From F03-T1: the sign-in code email uses template `email_code` (placeholders `seller_first_name`, `code`, `code_minutes`). It is `sensitive`, so it is never queued: when SES is down `send()` returns `{ status: "FAILED" }`, and the seller must be told the code couldn’t be sent.
