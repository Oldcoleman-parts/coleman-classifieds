## Scope

- [ ] `createInvitation()` (a transaction with the Listing; fee prefilled from promo/base and editable; offer scope) and the **Create invitation** screen: seller details, item summary, fee, offer scope, staff photos (F03 helper), the seller’s previous listings, and a copyable link + invitation email. _Built except the copyable invitation email, which waits for F03-FIX-3 (`renderTemplate`)._
- [x] `resolveToken()` (constant time; invalid, closed or expired states) and revoke; the 30-day expiry task registered with the scheduler.
- [x] Email code check (when `emailCodeRequired`): 6 digits, 15 min, max 5 attempts, a signed device cookie for 30 days.

## Out of scope

- Anything listed in other tickets or features.

## Acceptance criteria

- [x] A modified token shows the invalid page; a second listing per invitation is impossible.
- [x] A later Settings fee change doesn’t change a locked invitation.
- [x] A forwarded link on a new device can’t proceed without the code; brute force is locked after 5 attempts.
- [x] Tokens and codes never appear in logs.
- [x] `npm run test:ai` is green for this feature.

## Notes

_Record decisions (`// DECISION:`), deviations and follow-ups here. Code review and security audits are run on demand (`/review-all`), not per ticket._

- From F03-T1: every email is sent with `notifications.send(key, to, vars, { replyTo, idempotencyKey })`; template keys, placeholders and which are `sensitive` are in `app/modules/notifications/registry.js`. Links passed as placeholders must be https.
- From F03-T1: the sign-in code email uses template `email_code` (placeholders `seller_first_name`, `code`, `code_minutes`). It is `sensitive`, so it is never queued: when SES is down `send()` returns `{ status: "FAILED" }`, and the seller must be told the code couldn’t be sent.
- Built 2026-10-06 (module `access`, no schema change). The first scope item is built except the **copyable invitation email**: notifications can't render a `copyOnly` template with real values yet (follow-up on F03). The screen shows the copyable link; the box stays open until that lands.
- DECISION (deviation from `security-access`): Shopify's app proxy strips `Cookie` and `Set-Cookie`, so the device credential isn't an HttpOnly cookie. After a correct code the page keeps a signed, invitation-bound, 30-day credential in `localStorage` and sends it back as the `device` form field (or `X-CC-Device` header). The GET page never contains private details for an unverified device; a known device resumes by POST. Confirm the cookie stripping on the dev store; F04-T2 must keep the "verify by POST before private data" rule on every seller route.
- DECISION: the device key is HKDF(`TOKEN_PEPPER`, "cc-device-v1"): no new env var. Changing `TOKEN_PEPPER` invalidates every link and device.
- DECISION: an expired or revoked invitation's INVITED listing record is left as it is (closing it belongs to core; follow-up). Staff photos on it stay until then.
- DECISION: revoke only while the link is unused (invitation OPEN, listing INVITED); later, staff reject or remove (F05).
- DECISION: a LAPSED close keeps the link open, so a staff re-issue works with the same link. SOLD, REMOVED, EXPIRED and a rejection close it.
- DECISION: 5 wrong codes within an hour lock the invitation for the rest of that hour (worked out from `EmailCode` rows; only the newest code is checked; each try is counted before the comparison).
- DECISION: rate limits are in memory (one Railway instance): seller page 60/min per IP; code request 3/15 min per invitation and 10/hour per IP; code verify 20/15 min per IP. Honeypot on the code request form; no Turnstile, as the forms are behind the private link.
- DECISION: the offered fee is between 1 cent and the listing fee; the listing fee always comes from Settings. The offer scope is fixed to FIRST_MONTH until renewals are released.
- DECISION: the link uses the shop's primary domain (`shop.primaryDomain.url`, Admin 2026-10; the Dev MCP server wasn't available to validate it), falling back to `https://<shop>`. It is shown once after creation and never stored.
- DECISION: `InvitationCreated` is published after the creation transaction commits, because core doesn't export `recordEvent` (follow-up).
