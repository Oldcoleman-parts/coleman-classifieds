## Scope

- [x] Listing rules editor on the Settings screen: rules text (sanitised) with the current version shown; saving a changed text bumps `rulesVersion` through `core.updateSettings()`.
- [x] Features card (`/app/settings/features`): the alerts switch, plus renewals and open submissions only when `isReleased()`; a confirmation modal when turning a feature off; saves through `core.setFlag()` (`FeatureToggled`).

## Out of scope

## Acceptance criteria

- [x] Editing the rules text bumps the version and is audited; saving unchanged text doesn’t bump it.
- [x] Toggling alerts writes `FeatureToggled` with the staff email; unreleased features show no switch and can’t be turned on by a crafted request.
- [x] `npm run test:ai` is green for this feature.

## Notes

**Decisions**

- The listing rules are **plain text**, never HTML: line endings are normalised, control characters are stripped, and `<` or `>` is refused with a field error. Limit 1–20,000 characters (`core/settings.js`).
- Versions are numbered `v1`, `v2`, …; the seeded `draft-0` becomes `v1` on the first edit. Core sets the version inside the save transaction; a `rulesVersion` sent by the caller is refused. Two saves at the same moment can't publish the same version (the second gets a conflict).
- The `SettingsUpdated` audit entry holds the full old and new rules text and the old and new version. It is the only record of what an earlier version said.
- The rules editor is part of the existing Settings form and save bar (one save, one audit entry). `updateSettings()` now has ten editable settings (F02-T1 said nine).
- Features card: each feature is a status badge with a **Turn on** / **Turn off** button instead of a live switch, because React 18 doesn't bind change events on `s-switch`. Turn off opens an `s-modal`; the server also requires `confirmed=yes`.
- An unreleased feature is refused in both directions by `console.saveFeatureToggle()`, before core is called.
- `core.setFlag()` now does nothing (no save, audit entry or event) when the flag already has that value, and returns whether it changed.
- Navigation: a **Features** button on the Settings page and a breadcrumb back; no new entry in the app nav.

**Checks**

- Acceptance criteria are covered by `app/modules/core/tests/settings-rules.test.js`, `app/modules/console/tests/features.test.js` and `app/modules/console/tests/settings.test.js` (185 passed for `core` and `console`).
- No dev-store check of the two screens was recorded at close: the confirmation modal, the Features button and the breadcrumb are untested in the browser.
